2. Executive Summary
Modern data engineering and fintech platforms depend on a constellation of tools — Apache Airflow for orchestration, PySpark for large-scale processing, polyglot microservices for business logic, and Kafka-based systems for real-time trading — that together generate a high volume of metrics and logs. Existing observability options force a trade-off: commercial suites such as Datadog are comprehensive but prohibitively expensive, while a standalone ELK deployment is affordable but degrades under high-throughput, diverse-metric workloads.
This project delivers a Unified Observability Platform that ingests metrics and logs from Airflow, PySpark, microservices, and a Kafka-based trading system into a single, coherent, cloud-native stack. Prometheus collects and stores time-series metrics; the ELK Stack centralizes logs; Grafana and Kibana provide real-time visualization; and a FastAPI-based Metrics API, backed by Redis caching, exposes low-latency programmatic access for downstream consumers. The entire platform is containerized with Docker, orchestrated on Amazon EKS, and provisioned as code with Terraform — targeting validated operation at a 1–2 billion Kafka message scale.
The platform's core value proposition is combining data-pipeline observability and high-volume trading-system monitoring under one automated, open-source layer — something no single reviewed reference project offers — while remaining affordable, reproducible, and appropriate for both students learning observability concepts and practitioners running production-grade infrastructure.
3. Problem Statement & Motivation
3.1 The Core Problem
Modern data platforms must simultaneously manage Airflow DAGs, PySpark batch/streaming jobs, polyglot microservices, and high-throughput Kafka-based trading applications. Metrics and logs from these systems are typically scattered across disparate, poorly-integrated tools, making it difficult to maintain a single, trustworthy view of overall system health.
This fragmentation delays issue detection until after disruption has already occurred, and the operating cost of stitching together multiple monitoring tools grows with scale. Commercial all-in-one solutions such as Datadog address part of the problem but are prohibitively expensive for student teams, startups, and cost-conscious engineering organizations; relying solely on the ELK stack, on the other hand, introduces significant performance bottlenecks once metric volume and cardinality grow.
3.2 Why It Matters Now
Fintech and data platforms increasingly co-locate batch analytics (PySpark), workflow orchestration (Airflow), and real-time trading (Kafka) in the same environment — yet are monitored with disconnected tools.
Existing commercial APM/observability suites price out students, early-stage startups, and academic research environments.
Pure log-based stacks (ELK-only) do not scale gracefully to billion-message-per-day metric volumes without a dedicated time-series and caching layer.
Cloud-native, Infrastructure-as-Code deployment is now the default expectation for any credible observability product — ad hoc, manually-configured monitoring stacks are no longer acceptable.
3.3 Supporting Literature
The proposal is grounded in five peer-reviewed references spanning IEEE Transactions on Services Computing, IEEE CLOUD, and related venues (see Section 14, References), covering dynamic observability frameworks for distributed microservices, AI-driven autonomous data-pipeline management, intent-driven multi-engine observability for geo-distributed clouds, LLM-enabled microservice monitoring, and cross-domain telemetry architectures. These works collectively motivate the multi-engine, intent-driven, and automation-first design adopted here.
4. Goals & Objectives
4.1 Primary Objectives
Design and develop a unified observability platform that monitors Apache Airflow, PySpark, microservices, and high-volume trading systems end-to-end.
Collect and store metrics using Prometheus and logs using the ELK Stack, and provide real-time visualization and alerting using Grafana.
Build a high-performance Metrics API using FastAPI, enhanced with Redis caching and Kafka integration, for fast and reliable query responses.
Deploy the complete platform in a containerized, cloud-native environment using Docker, Kubernetes (Amazon EKS), and Terraform on AWS.
Evaluate the platform's monitoring performance and cost-efficiency against existing observability solutions (Datadog, standalone ELK) under simulated high-volume data and trading workloads.

6. Scope
6.1 In Scope
Collection of metrics and logs from Airflow, PySpark, selected microservices, and Kafka-based components of the trading system.
A high-performance Metrics API (FastAPI + Redis) and Grafana dashboards for visualization.
Fully containerized deployment (Docker) orchestrated on Kubernetes (Amazon EKS).
Infrastructure as Code for all AWS resources (VPC, EKS, ALB, ElastiCache) via Terraform.
Sample microservices and a Kafka producer to simulate realistic trading and pipeline workloads for validation.
6.2 Out of Scope (Current Version)
Full distributed tracing (span-level tracing across services) — deferred to future scope.
A complete trading exchange — microservices represent trading-system behavior, not a production exchange.
Multi-region deployment — the initial version is restricted to a single AWS region.
AI-driven anomaly detection and automated self-healing beyond Kubernetes-native capabilities.
6.3 Future Scope
Distributed tracing integrated via OpenTelemetry spans.
AI-driven anomaly detection over Prometheus/ELK data.
Multi-region, multi-cluster deployment for geo-distributed resilience.
Automated alerting escalation policies and self-healing runbooks.
7. System Architecture
The platform follows a five-layer architecture. Data-generating components emit telemetry, which passes through a collection layer, into dual storage engines, and is finally surfaced through an API/visualization layer — all running on a containerized, IaC-provisioned infrastructure layer.
7.1 Layered Architecture Overview
Layer
Components
Responsibility
1. Data Sources
Apache Airflow (DAG orchestration), PySpark Jobs (batch analytics), Microservices (REST/gRPC APIs), Trading Platform (Kafka, high volume)
Generate raw metrics, logs, and events
2. Collection
OpenTelemetry Collector, Prometheus Exporters
Standardize and forward traces, metrics, and logs from every source
3. Storage & Processing
Prometheus (time-series metrics), ELK Stack — Elasticsearch + Logstash (log indexing)
Persist and index metrics and logs for querying
4. API & Visualization
FastAPI Metrics API, Redis (query cache), Grafana (metrics dashboards), Kibana (log analysis)
Expose low-latency query endpoints and render real-time dashboards
5. Infrastructure
Docker (containerization), Amazon EKS / Kubernetes (orchestration & auto-scaling), Terraform on AWS (IaC)
Package, deploy, scale, and manage the full stack
7.2 Data Flow
Data Sources emit metrics via Prometheus-format exporters and logs/traces via OpenTelemetry client libraries.
The Collection layer (OpenTelemetry Collector + Prometheus exporters) receives and standardizes this telemetry.
Metrics flow into Prometheus; logs flow into the ELK Stack (Elasticsearch, indexed via Logstash).
The FastAPI Metrics API queries Prometheus, using Redis as a query cache to serve sub-millisecond responses to repeated queries.
Grafana renders Prometheus-backed dashboards; Kibana provides a dedicated log-analysis interface over Elasticsearch.
The entire stack is containerized with Docker, deployed on Amazon EKS, and provisioned end-to-end with Terraform.

8. Functional Requirements
8.1 Metrics Collection
FR-1: The system shall scrape and store time-series metrics from Airflow, PySpark, microservices, and the Kafka-based trading platform via Prometheus.
FR-2: The system shall support Prometheus alerting rules for threshold-based conditions (e.g., DAG failure rate, consumer lag).
8.2 Log Aggregation
FR-3: The system shall ingest logs from all monitored components into Elasticsearch via Logstash pipelines.
FR-4: The system shall provide full-text, filterable log search through Kibana.
8.3 Metrics API
FR-5: The system shall expose a FastAPI-based REST API for querying current and historical metrics.
FR-6: The Metrics API shall cache frequently requested queries in Redis to minimize repeated Prometheus load.
FR-7: The Metrics API shall expose endpoints consumable by downstream systems (e.g., internal dashboards, risk engines).
8.4 Visualization & Alerting
FR-8: The system shall provide pre-built Grafana dashboards for pipeline health, trading-system performance, and overall system status.
FR-9: Grafana shall support configurable alerting and SLO tracking.
8.5 Deployment & Infrastructure
FR-10: All platform components shall be packaged as Docker containers.
FR-11: The platform shall be deployable and horizontally scalable on Amazon EKS with Kubernetes-native auto-scaling.
FR-12: All AWS infrastructure (VPC, EKS, ALB, ElastiCache) shall be provisioned and version-controlled via Terraform.
8.6 Workload Simulation
FR-13: The system shall include sample microservices and a Kafka producer capable of generating realistic pipeline and trading workloads for validation and benchmarking.

11. Data & API Design
11.1 Metrics Data Model (Prometheus)
Metrics follow standard Prometheus time-series conventions: a metric name, a set of key-value labels identifying source (e.g., component="airflow", dag_id, job, service), and a timestamped numeric value. Suggested label conventions:
component: airflow | pyspark | microservice | kafka-trading
environment: dev | staging | prod
severity (for alerting rules): info | warning | critical
11.2 Log Data Model (ELK)
Logs are shipped through Logstash into Elasticsearch with a normalized schema including: timestamp, component, log_level, message, trace_id (where available), and source_host, enabling consistent cross-component search in Kibana.
